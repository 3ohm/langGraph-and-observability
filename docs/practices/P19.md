# P19: Read-only, least-privilege access

## Problem

A triage agent reads a cluster, a monitoring account and source code. If it can write, a prompt injection in a log line or a bug in a step can change production. Broad cloud permissions turn a leaked pod token into an account-wide incident.

## What the template does

- Kubernetes: one ClusterRole with only the verbs `get` and `list`, on pods, pod logs, events, nodes and the workload kinds. No `watch`, `create`, `patch`, `delete` or `exec`.
- AWS (EKS Pod Identity or IRSA): exactly `bedrock:InvokeModel`, `sqs:ReceiveMessage`, `sqs:DeleteMessage`, `sqs:ChangeMessageVisibility`, `sqs:SendMessage` (results only), `ecr:BatchGetImage` and `ecr:GetDownloadUrlForLayer`, each scoped to its resource.
- Postgres: the worker connects as `lps_app`, which can read and write rows but not change the schema (P4).
- Git: source checkouts fetch only from `APP_GIT_ALLOWED_HOSTS`, the only hosts that receive `APP_GIT_TOKEN`. Use a read-only token scoped to the repositories the agent needs.
- The container runs as a non-root user with a read-only root file system, no privilege escalation and every capability dropped. Secrets come only from Secret references.
