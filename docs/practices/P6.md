# P6: Retention for checkpoints and results, run by one leader

## Problem

Every step of every run writes a checkpoint, so the checkpoint tables grow without end. Deleting from LangGraph's tables with raw SQL breaks when the library changes its schema, and several pods pruning at once waste work and deadlock each other.

## What the template does

- The worker makes a retention pass at start and then every hour (`prune_once`).
- A pass first takes the session advisory lock `hashtext('lps:prune')`. A pod that does not get it returns at once.
- Checkpoints: for finished runs (`success`, `failed`) that ended more than `APP_RETENTION_CHECKPOINT_DAYS` (14) ago, it calls `saver.aprune(thread_ids, strategy="delete")` in batches of 100, never SQL on LangGraph's tables.
- Results: rows older than `APP_RETENTION_RESULT_DAYS` (90) go through each agent's `retention_sql`, then the `runs` rows go. A run's row goes only after its checkpoints.
- Each batch locks its runs with `FOR UPDATE SKIP LOCKED`; batches retry on `SerializationFailure` and `DeadlockDetected`.
- Behind PgBouncer in transaction mode (`APP_PGBOUNCER_MODE=true`) the lock and its unlock may run on different server sessions, so a single leader is best effort: two pods may prune at once, and a lock left on a server session makes the other pods skip their passes until PgBouncer closes that session. That stays correct, because each batch locks its rows with `SKIP LOCKED` and `aprune(strategy="delete")` is idempotent.
- Run `migrate` on a direct DSN (`APP_MIGRATION_DATABASE_URL`), not through PgBouncer.
