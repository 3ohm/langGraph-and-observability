# P13: Idempotent publishing

## Problem

Publishing the result is the one step with an effect outside the process. A crash after the send and before the step's checkpoint makes the step run again on resume (P11), and the consumer gets the result twice.

## What the template does

- `run_once` (the action ledger) runs a side effect once per idempotency key. It records each finished action in `action_ledger` with a hash of its arguments and the result it returned.
- A later call with the same key and arguments gets the recorded result back and does not run the action again; other arguments raise `LedgerConflict`.
- Calls with one key, in any process, run one at a time: the ledger's transaction holds `pg_advisory_xact_lock(hashtextextended(key, 0))`.
- Exactly once covers the record, not the outside world: a crash between the send and its ledger row sends again. So give the receiving system the ledger key as its idempotency key; an SQS FIFO queue drops the repeat by its deduplication ID.
- The example's `publish` step inserts the result with `ON CONFLICT (run_id) DO NOTHING`, then sends it to each sink through `run_once` with the key `publish:<run_id>:<sink>`.
