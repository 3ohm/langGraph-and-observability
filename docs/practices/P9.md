# P9: Leases, heartbeats, periodic recovery

## Problem

A pod that dies from OOMKill, SIGKILL or node loss runs no shutdown code. Without an owner and an expiry on each run, its runs stay "running" for ever, or two pods pick up the same run.

## What the template does

- A pod claims a run under a lease: `status = 'running'`, `lease_owner` is its pod name (`POD_NAME`), `lease_expires_at` is now plus `APP_LEASE_SECONDS` (60). Lease times come from the database clock, so pods agree on expiry.
- Every `APP_HEARTBEAT_SECONDS` (15) the pod extends the leases of its own runs.
- Recovery, at start and every `APP_RECOVERY_INTERVAL_SECONDS` (30), claims pending runs and running runs whose lease has expired, oldest first and at most the free slots, with `FOR UPDATE SKIP LOCKED`, so two pods never take the same run.
- `mark_success`, `mark_error` and `release` change a run only while the caller still holds its lease: a pod that lost the lease changes nothing.
- An error returns the run to pending with one more attempt; after `APP_MAX_ATTEMPTS` (3) it is `failed`. `python -m langgraph_and_observability runs retry RUN_ID` returns a failed run to pending.
- A reclaim of a run whose lease expired counts as an attempt too: its pod died without ending it. The reclaim that reaches `APP_MAX_ATTEMPTS` sets the run `failed`, with the error `LeaseExpired`, so a run that kills its pod each time (OOMKill) stops. A drained run (SIGTERM, P10) goes back to pending with no attempt counted.
