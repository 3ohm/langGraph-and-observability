# P12: Explicit retry, timeout and error-handler defaults (spec 6.5)

## Problem

LangGraph's `default_retry_on` never retries `TimeoutError` (an `OSError`), retries raw `httpx` errors only on 5xx, and retries provider-SDK errors that it does not recognise, 400s included. Stacked on the SDKs' own retries, that multiplies attempts and repeats requests that can never succeed. A node with no timeout can hang a run until its deadline.

## What the template does

- One retry layer per external call: the client library's own (botocore standard mode with `max_attempts` 3, the Datadog client's `enable_retry`). The graph does not retry those clients' errors again.
- `default_retry_policy()`: at most 3 attempts with jittered backoff, for what `is_transient` accepts only: connection errors, timeouts, Postgres serialization failures, deadlocks and operational errors, the Datadog transport's timeouts, and a Kubernetes 429 or 5xx. Never another 4xx.
- `step_timeout(seconds)`: a `TimeoutPolicy` that caps one attempt of a node. Every node is `async`, because node timeouts work only on async nodes.
- The example sets both on every node, with its own timeout per node, and gives `collect_datadog` and `collect_code` error handlers: a step that fails for good adds a note naming the error's type, and the run goes on.
- The core rules are proven on the test-only graph and a table of exceptions, so they survive the removal of the example agent.
