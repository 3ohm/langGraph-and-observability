# P4: Migrations as a separate step; minimal database roles

## Problem

Migrations that run when each replica starts race each other, and they need a role that can change the schema, which the running app should never hold. `AsyncPostgresSaver.setup()` also runs `CREATE INDEX CONCURRENTLY`, which needs autocommit and no other open transaction.

## What the template does

- Plain-SQL migrations, forward-only and numbered, one folder per component: core, then LangGraph's `setup()`, then the worker, then each registered agent. `schema_migrations` records each `(component, version)`, so a second run applies nothing.
- One runner at a time: it holds the session advisory lock `hashtext('lps:migrate')`, polled with `pg_try_advisory_lock`, so it never blocks `CREATE INDEX CONCURRENTLY`. A file with `-- migrate:no-transaction` runs outside a transaction.
- `python -m langgraph_and_observability migrate` is a one-shot step: the `migrate` service in Compose, the `migrate` Job on Kubernetes. The worker never migrates.
- Two roles (`deploy/sql/roles.sql`): `lps_migrator` runs DDL through `APP_MIGRATION_DATABASE_URL`; `lps_app`, the worker's `APP_DATABASE_URL`, can only read and write rows.
- CI builds the image and runs its `migrate` command against an empty Compose Postgres.
