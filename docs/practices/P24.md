# P24: Long-term memory in the Postgres Store

## Problem

A checkpoint belongs to one thread, and each run is its own thread, so what one run learns is gone for the next. An agent that must remember across runs, such as past incidents for each workload or a user's preferences, needs a store that outlives a thread. A second database for it is one more system to run, back up and secure.

## What the template does

- `make_store` builds LangGraph's `AsyncPostgresStore` on the same pool as the checkpointer, and the worker compiles every graph with it. A node reads and writes long-term memory through `runtime.store` (`aget`, `aput`, `asearch`), by namespace and key.
- The upstream Store takes no shared lock on a pool: each call checks out its own connection (compare P3). It also works on a PgBouncer-mode pool, whose connections never prepare a statement (P2).
- `migrate` creates the Store's tables (`AsyncPostgresStore.setup()` in the `langgraph` component), never the worker (P4). A second `migrate` changes nothing, and the app role gets row access to the tables through the default privileges of `deploy/sql/roles.sql`.
- `langgraph dev` (`make studio`) and the Agent Server bring their own store on their path. The Postgres Store is the worker's.
- The Store keeps no secrets. Its values are plain JSON in Postgres: no serde allowlist and no encryption at rest (P7 covers checkpoints only). Redact what a node remembers (AGENTS.md rule 3).
- No index and no TTL by default. `index=` adds semantic search on pgvector, which the Compose image has; `ttl=` makes items expire. The pruner (P6) does not delete Store items.
