# P8: Queue intake: validate, dedup, record, then delete; bad messages go to the DLQ

## Problem

A worker that deletes a message only after the whole run needs a visibility timeout longer than any run, and a crash mid-run redelivers the message to a second pod. A worker that deletes first loses the work when it crashes. Bad messages either loop for ever or vanish without a trace.

## What the template does

- `SqsIntake.poll` long-polls SQS (`APP_SQS_WAIT_SECONDS`, 20) for at most as many messages as the worker has free run slots.
- Each body is parsed as JSON and validated with the agent's `input_model`. An invalid message is logged as `intake.invalid`, with the error's type and location but never the body, and is not deleted: SQS delivers it again and then moves it to the dead-letter queue after `maxReceiveCount` (3 in the local ElasticMQ config).
- The agent's `dedup_key` maps the input and the send time to a key, and the run is inserted with `ON CONFLICT (dedup_key) DO NOTHING`. A second message with the same key is logged as `intake.duplicate`.
- Then the message is deleted. From here Postgres owns the run (P9), so the visibility timeout only has to cover validate, insert and delete.
- boto3 is synchronous, so each SQS call runs in a thread.
- The proof uses the test-only `test_steps` graph, so it survives the removal of the example agent.
