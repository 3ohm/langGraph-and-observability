# P18: Provider constraints: no sampling parameters, no forced tool choice, refusals handled

## Problem

Claude Opus 5.5 on Bedrock rejects `temperature`, `top_p` and `top_k`, a forced tool choice and an assistant prefill with a 400, so old "force a tool to get JSON" code fails. A reply can also stop with `stop_reason: "refusal"` or `"max_tokens"`, and code that expects an answer then crashes or stores half a reply.

## What the template does

- The request body has no `temperature`, `top_p`, `top_k`, `tools`, `tool_choice` or `thinking` field and no assistant prefill. Structured output comes from `output_config.format` (P16), and `effort` (`APP_MODEL_EFFORT`, `medium`) is the control.
- `max_tokens` is `APP_MAX_OUTPUT_TOKENS` (16000).
- `refusal`: the step returns no analysis and `refusal=True`; the result is marked `needs_human`. No retry, no crash.
- `max_tokens`: the reply counts as invalid, even when it parses, and gets the one repair attempt (P16).
- botocore retries throttling itself, in standard mode; the graph does not retry botocore errors (P12).
- The LLM judge of the evals sends the same kind of request.
